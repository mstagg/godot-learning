Lesson 5 · Breakout clone · about 45 minutes, or two sittings

A game with an ending

Lives, a game over that freezes the game, and a level clear: game states, pausing, and counting what's left.

Your win

Breakout becomes a real game. You get three balls. Losing the last one freezes everything behind GAME OVER until you press a button, and clearing the wall moves you to level 2. You can explain why pausing the root did nothing until you un-paused one branch, and why counting the bricks that are left is harder than it looks.

From last time

Delta, third time: both bodies collide; the paddle stops at the walls. The difference is the argument. move_and_collide(motion) wants a distance, so the ball passes velocity * delta_sec. move_and_slide() reads self.velocity, a speed, and multiplies by delta itself. That's why the paddle's _delta_sec is unused.

Nine-patch: it doesn't interpolate, so no new pixels are invented. The corners stay fixed, and the edges and centre stretch. fit() sizes the patch in art pixels and then scales it ×2, so every art pixel is a 2×2 block, the same as the ball's. With size = target_size, your outline would be half as thick as the ball's pixels.

Filter: under Linear, the 2× art would go soft, and the black outline would smear into the brick colour.

Right now a miss resets everything, and the game never ends. This lesson gives it a beginning, a middle and an end. The engine ideas are small, but every game you make from here on needs them: Galaga's waves, Tetris's top-out, a pause menu, and the tactics game's turn phases are all states with an owner.

Four ideas, in fifteen minutes

1. A game state is one variable with one owner

You could track this with booleans: is_game_over, is_level_clear. Two booleans give four combinations, and one of them, "game over and level clear", is nonsense that your code must never reach. An enum makes impossible combinations impossible to write:

enum State { PLAYING, GAME_OVER, LEVEL_CLEAR }

var _state: State = State.PLAYING


func _set_state(new_state: State) -> void:
	self._state = new_state
	match new_state:
		State.PLAYING:
			...
		State.GAME_OVER:
			...

Put every change through one function. Then "what happens when we enter GAME_OVER" lives in one place, not in whichever handler happened to notice. The owner is the game root, game.gd, which already owns the score. Lives move up there too. The play area reports what happened (a ball was lost, the last brick broke), and the root decides what that means. It's call down, signal up again, one level higher.Game Programming Patterns: State. Read up to "Finite State Machines"; the rest is more than Breakout needs.

The alternative people reach for is an autoload, a global singleton. It's the right tool when state must survive scene changes, which is what the Zelda clone needs. Here everything lives in one scene, so the root is enough.

2. Pausing: get_tree().paused and process_mode

Setting get_tree().paused = true stops the _process, _physics_process and input callbacks of every node that is pausable, and it freezes physics for them. Each node's Process → Mode in the Inspector decides whether it's pausable:Docs: Pausing games and process mode.

ModeRuns when…
Inherit (default)whatever its parent does
Pausablethe tree is not paused
When Pausedthe tree is paused (pause menus)
Alwayseither way
Disablednever

Here's the trap, checked in 4.7.2. Your game root must keep running while paused, because it's the node listening for "press Enter to play again", so you set it to Always. But every child set to Inherit now inherits Always too, so pausing does nothing at all. The fix is to set the branch that should freeze, the GameWindow container, back to Pausable. Then everything under it, the ball and paddle included, inherits Pausable.

Pausing doesn't stop everything. Paused nodes are still drawn, so your GAME OVER message can live inside the frozen play area. And method calls and signal callbacks still run on a paused node. The root can call show_message() on the play area while it's frozen. That cuts both ways, as one exercise below will show.

3. Counting what's left, when deletion is late

Level clear means "no bricks left". The obvious check is self._bricks.get_child_count() == 0 in _on_brick_destroyed. But hit() emits destroyed and then calls queue_free(), and queue_free() doesn't delete until the frame ends. When the last brick reports in, it's still a child, and I confirmed the count is 1, not 0. You'd never detect the level clear.

There are three ways out. You could skip nodes where is_queued_for_deletion() is true, connect each brick's tree_exited signal, or keep your own counter: set it when the grid is built and decrement it on each destroyed. The counter is the simplest and the easiest to review. Whatever you pick, your spec should name it.

4. CanvasLayer for messages over the game

A CanvasLayer draws its children on a separate layer, above the normal 2D scene, and ignores any camera. A Control under it anchors to the edges of the viewport the layer is in. Inside your SubViewport, that's exactly the play area. So CanvasLayer → CenterContainer (Full Rect) → Label centres a message over the play area at any window size, with no position maths. Every HUD you build later starts like this.Docs: Canvas layers.

Restarting also needs a new input action. Call it confirm, and bind Enter, Space and the gamepad's bottom face button, which is A on a Steam Deck. A one-off press is an event, so handle it in _unhandled_input(event) with event.is_action_pressed("confirm").

Do it

Use /feature-spec for each spec, and write your own before opening each model. The agent builds a whole spec at once; review it as one diff.

  1. Spec 0021: lives. Decide: who owns the lives, how a miss gets from the drain to that owner, what a miss now does to the bricks (this changes 0013's behaviour), and what happens on the last life before there's a game-over screen.
    Model spec (open after writing yours) 
    # 0021 · Lives
Goal: I get three balls; a miss costs a life instead of rebuilding the wall.
Behaviour:
- game.gd owns _lives (@export var starting_lives: int = 3); its setter calls GameStateWindow.set_lives(), like _score_total.
- New LivesLabel under the score: "Lives 3".
- The drain no longer calls reset_game. game_window.gd re-emits it, still deferred, as ball_lost.
- reset_game splits: reset_ball() returns the paddle to the centre and calls paddle.hold_ball(ball); build_level() rebuilds the bricks, then calls reset_ball().
- With lives left, game.gd calls reset_ball(); broken bricks stay broken.
- On the last life, for now, it all restarts: lives and score back to start, build_level().
Done when:
- "Lives 3" shows at start, and each miss drops it by one, with the broken bricks still gone.
- After the third miss: Lives 3, score 00000, full wall.
Not in this spec:
- A game-over screen or pausing
- Ball icons instead of a number
- Extra lives from score

    Review questions. Is the drain still connected deferred? If not, build_level() adds bricks mid physics step, the bug you fixed in lesson 2. Does a window resize still call build_level() from inside game_window.gd? And is reset_game gone completely, not left dangling?

  2. Spec 0022: game over. Decide: the state names, where the message lives, which nodes get which Process Mode, the input action and its bindings, and what a restart resets.
    Model spec (open after writing yours) 
    # 0022 · Game over
Goal: Losing the last ball freezes the game behind GAME OVER until I press a button to play again.
Behaviour:
- game.gd gets enum State { PLAYING, GAME_OVER } and _state; every change goes through _set_state().
- The play area gets CanvasLayer > CenterContainer (Full Rect) > Label "Message", hidden; game_window.gd has show_message(text) and hide_message().
- Last life lost: GAME_OVER, get_tree().paused = true, show "GAME OVER\nPress Enter".
- Process Mode: Game root Always; GameWindow (the SubViewportContainer) Pausable.
- New input action confirm: Enter, Space, gamepad bottom button. game.gd's _unhandled_input uses it only in GAME_OVER.
- Confirm: lives and score reset, build_level(), hide_message(), unpause, PLAYING.
Done when:
- After the third miss, the ball and paddle freeze and GAME OVER shows centred in the play area.
- The arrow keys do nothing while it shows; Enter starts over at 00000, Lives 3, full wall.
- Enter mid-game does nothing.
Not in this spec:
- Title screen
- High scores
- A pause key during play
- Animating the message

    Review questions. Did the agent set Process Mode on the right two nodes, and on nothing inside the play area? Does _set_state() do the pausing, or is paused = true scattered across handlers? And is 0021's "restart on the last life" code replaced, not left beside the new path? Last, Space is now bound to both confirm and your launch: does one press at GAME OVER restart the game and launch the ball? Try it, and decide whether that's a bug.

  3. Break it on purpose. Set GameWindow's Process Mode back to Inherit, play to game over, and watch. Describe what you see and why, using the table in idea 2. Then undo it with git checkout.
  4. Spec 0023: level clear, with no model. Write this one alone. Decide how the play area knows the last brick went (idea 3), what it tells the root, what the message says, what carries over to level 2 (score? lives? ball speed?), and how LevelLabel stops being hard-coded. Level 2 is the same wall.
  5. Have the agent stress-test your states. Before implementing 0023, ask: "Make a table with every state in game.gd as rows (PLAYING, GAME_OVER, LEVEL_CLEAR) and every event as columns: ball drained, last brick broken, confirm pressed, window resized. In each cell, say what specs/0023 plus the current code would do, and mark every cell the spec leaves undecided." Decide each marked cell, and put the decision in the spec or under "Not in this spec". Watch the resize column. Signal callbacks run while paused (idea 2).
  6. Run it and check. Check every "Done when" line in all three specs. Then lower brick_rows and brick_columns to 1 in the Inspector, so a level clear takes seconds to test, and set them back afterwards.

Push it further

This is the last Breakout lesson. These are open-ended, with no model specs: walk your own path and write each one with /feature-spec.

  • A fuller state machine. Since 0018, "ball on the paddle" is really its own state. Is it SERVING, or still PLAYING with a held ball? Add a pause key (PAUSED) and decide which states it works in. Watch for when the state table outgrows one match.
  • Distinct levels. Describe each wall as data, for example an array of strings where # is a brick and . is a gap, and have build_level() read level n. Decide what happens after the last level. This is a step toward Tetris's lesson on Resources.
  • Difficulty per level. Change the starting ball speed or paddle_influence per level, from the same level data.
