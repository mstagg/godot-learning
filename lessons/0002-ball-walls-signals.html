Lesson 2 · Breakout clone · about 40 minutes

A ball that bounces

Collisions, layers and your first signal, built from three small specs.

Your win

A ball launches, bounces off the walls and your paddle at constant speed, and when it falls off the bottom the game notices and serves a new one. You write three specs, review every step, and can explain what a signal is and who listens to it.

Lesson 1 gave you a body that your code moves. Today's ball is the same kind of body, but this time the interesting part is what happens when it hits something. The second half of the lesson covers signals, the way one node tells the rest of the game that something happened. Signals are the main way scenes talk to each other in Godot, and nearly every later clone leans on them.

Three ideas, in ten minutes

1. A Breakout ball is a CharacterBody2D, not a RigidBody2D

Last lesson's question still picks the body: who controls the movement? A real physics ball would speed up, slow down and spin. Breakout wants the opposite: constant speed and predictable angles. So your code stays in charge and the ball is a CharacterBody2D again.

The difference from the paddle is the call. move_and_slide() slides along what it hits, which is right for walking. A ball must bounce, so it uses move_and_collide(). It moves by a motion vector, stops at the first thing it hits, and returns a collision object (or null if nothing was hit).Docs: Using CharacterBody2D. Shows move_and_collide returning a KinematicCollision2D and bouncing with velocity.bounce(collision.get_normal()).

func _physics_process(delta: float) -> void:
	var collision := move_and_collide(velocity * delta)
	if collision:
		velocity = velocity.bounce(collision.get_normal())

Look at the delta. move_and_collide() takes a distance for this tick, not a velocity, so here you do multiply by delta. move_and_slide() doesn't, move_and_collide() does. Agents mix these up, so it's the first thing to check in the ball script.

The normal is the direction the surface faces. bounce() reflects the velocity around it, like a billiard ball off a cushion.

2. Layers say what you are, masks say what you notice

Every collision object has a layer (which channels it lives on) and a mask (which channels it scans for).Docs: Collision layers and masks. "The collision layer describes where a node appears. The collision mask describes what a node scans for." A collision happens when one object's mask includes the other's layer. Everything starts on layer 1 with mask 1, so by default everything hits everything. You've lived with that so far.

You need layers today for one reason: the bottom-edge zone should react to the ball, not to the paddle or anything else that wanders in. Give the ball its own layer, and let that zone's mask watch only that layer. Name the layers in Project Settings → Layer Names → 2D Physics, so the Inspector shows names, not numbers.

3. Signals: "call down, signal up"

A signal is an event a node announces. Any other node can connect a function to it, and Godot calls that function when the signal is emitted.Docs: Using signals. Signals are Godot's observer pattern: the emitter doesn't know or care who is listening. It is the observer pattern with the wiring built into the engine.

Today's signal comes built into Area2D: body_entered fires when a physics body overlaps it. The bottom-edge zone is an Area2D. Code in the main scene connects to it:

@onready var _drain: Area2D = $Drain

func _ready() -> void:
	_drain.body_entered.connect(_on_drain_body_entered)

func _on_drain_body_entered(_body: Node2D) -> void:
	# ball fell off the bottom: serve a new one
	...

The rule your CLAUDE.md already states, in one line: a parent calls down to its children with method calls, and a child signals up to its parent. The drain doesn't know the main scene exists. That's what lets you reuse a scene somewhere else unchanged. When you review agent code, a child calling get_parent().something() is the smell to catch.

Do it

  1. Predict the node tree. On paper, write what main.tscn will contain once it has a paddle, a ball, three walls and a drain. Which are bodies, which is an area, which are scene instances? Don't look anything up. You'll compare in step 7.
  2. Write spec 0004: walls. Create specs/0004-walls.md, at most 10 lines: three StaticBody2D walls (left, right, top), no wall at the bottom, no visible art. Say how thick they are and where "Not in this spec" draws the line. The paddle's existing clamp stays: removing it is a tempting extra. Then compare with the model below.
    Model spec (open after writing yours) 
    # 0004 · Walls

Goal: the play area has solid walls on the left, right and top.

Behaviour:
- Three StaticBody2D walls just outside the viewport edges, 20 px thick.
- Walls sized from the viewport at start, not hard-coded to 1152x648.
- Nothing along the bottom edge.

Done when:
- Running the game shows no visible change, and the Remote tab shows three wall bodies at the edges.

Not in this spec:
- Ball, drain, collision layers, removing the paddle clamp, visible walls.

    "Done when" is a weak check here because nothing looks different yet. That's fine: a spec can set up the next one. The ball spec is where it becomes visible.

    Build it with: "Implement specs/0004-walls.md one step at a time. Stop after each step." Review each stop with the checklist, then commit.
  3. Write spec 0005: the ball. Create specs/0005-ball.md. Include the starting position, a speed in an @export variable, the launch angle, and what it bounces off. Write the bounce rules for the paddle too, since the paddle is already a body. Leave out the drain and any scoring. Then compare with the model.
    Model spec (open after writing yours) 
    # 0005 · Ball bounces

Goal: a ball launches from the paddle and bounces around the play area.

Behaviour:
- Ball is a CharacterBody2D with a ColorRect, 16x16, as its own scene.
- Starts above the paddle's centre and launches at 400 px/s, up and slightly right.
- Uses move_and_collide; reflects off walls and the paddle with velocity.bounce().
- Speed stays constant after every bounce (re-normalise the velocity).
- Speed is an @export var.

Done when:
- Ball bounces off the left, right and top walls and the paddle, and never slows or speeds up.
- Ball falls out of the bottom and keeps going (that's expected).

Not in this spec:
- Drain, respawn, bricks, paddle-angle control, spin, sounds.

    The bug to look for in review: speed that drifts after many bounces. Floating-point rounding is why the model spec asks for re-normalising.

    Build and review it the same way, then commit.
  4. Write spec 0006: the drain. Create specs/0006-drain.md. The bottom of the screen gets an Area2D that emits a signal when the ball enters, and the main scene responds by putting the ball back above the paddle and relaunching it. The spec must say which node listens to which. Use the layers idea from the lesson so only the ball triggers it. Then compare with the model.
    Model spec (open after writing yours) 
    # 0006 · Drain and relaunch

Goal: when the ball falls off the bottom, a new one is served.

Behaviour:
- Name 2D physics layers: walls, paddle, ball.
- Drain is an Area2D below the bottom edge; its mask watches only the ball layer.
- Main connects to the drain's body_entered signal and resets the ball above the paddle, relaunching it.
- The drain does not reference main or the ball directly.

Done when:
- Letting the ball fall always serves a new ball. The paddle never triggers the drain.

Not in this spec:
- Lives, game over, score, delays or animations, scene reloading.

    Notice "the drain does not reference main". That sentence is the whole "signal up" rule, written as a testable line.

    Build and review it, then commit. In the review, find the line that connects the signal and read it aloud: who is the emitter, and who is the listener?
  5. Run it and compare. Open the editor (godot --path ~/learning/godot/projects/breakout/breakout -e) and run the project. Check each "Done when" line. Then open main.tscn and compare the Scene dock with your prediction from step 1.
  6. Break it on purpose. In ball.gd, change the line that moves the ball to move_and_collide(velocity), without the delta. Run it and describe what you see, and why. Then undo the change. (One git checkout does it.)
  7. Take the quiz below, from memory.
