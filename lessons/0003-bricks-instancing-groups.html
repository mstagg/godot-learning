Lesson 3 · Breakout clone · about 45 minutes

Bricks to break

Making scenes from code, tagging nodes with groups, and a signal that carries a score.

Your win

A wall of bricks fills the top of the screen. When the ball hits a brick, the brick disappears and your score goes up. You write four small specs, review every step, and can explain how one scene becomes fifty nodes at runtime.

From last time

Delta: both bodies collide. The difference is the argument. move_and_collide(motion) takes a distance for this tick, so you pass velocity * delta. move_and_slide() reads the velocity property and applies delta itself. If you pass a motion in, you multiply. If you set velocity, you don't.

Body or area: a StaticBody2D drain would be solid, so the ball would bounce off the bottom like a fourth wall. It also has no body_entered signal, because nothing can overlap it. An Area2D is the "notice, don't block" node.

So far, every node in the game was placed by hand: one paddle, one ball, three walls, one drain. Breakout needs dozens of identical bricks, and placing those one by one in the editor would be slow and fragile. This lesson has the game build them from code. It also adds a way to label a whole set of nodes at once, and a signal that carries a value. Every later clone relies on these three: Galaga's enemy waves, Tetris's pieces, and the tactics game's units are all scenes made from code, tagged and counted.

Three ideas, in ten minutes

1. A scene file is a template; instantiate() makes a copy

Loading a .tscn gives you a PackedScene: the saved scene, not yet a node. Calling instantiate() on it builds a fresh tree of nodes from that template. Then you have to add the new node to the tree with add_child(). Until then it exists in memory, but it isn't drawn, doesn't collide, and its _ready() hasn't run.Docs: Nodes and scene instances. Covers preload, instantiate() and add_child().

const BRICK_SCENE: PackedScene = preload("res://scenes/brick.tscn")

func _spawn_brick(at: Vector2) -> void:
	var brick: Brick = BRICK_SCENE.instantiate()
	brick.position = at
	self.add_child(brick)

preload loads the file once, when the script is parsed. That's right for a scene you'll use many times. The project's alternative is an @export var brick_scene: PackedScene that you fill in through the Inspector. Either is fine, and the spec should say which.

Nodes made at runtime don't appear in the editor's Scene dock, because that only shows what's saved in the .tscn. To see them, run the game and open Scene → Remote. That's where you'll check your brick grid.

2. Groups are tags

A group is a named tag on a node. A node can be in any number of groups, and a group can hold nodes of any type, anywhere in the tree.Docs: Groups. Add groups in the Node dock's Groups tab, or with add_to_group() in code. Three calls cover most uses:

self.add_to_group("bricks")                                   # tag me
collider.is_in_group("bricks")                                # is that a brick?
self.get_tree().get_nodes_in_group("bricks").size()           # how many are left?

Groups differ from class_name in one useful way: a group asks "what role does this play?", not "what script does it run?" A later "breakable" group could include bricks, a boss and a destructible wall, all with different scripts.

The trap to catch in review: queue_free() doesn't delete a node immediately. It marks it for deletion at the end of the frame. Until then, the node is still in its groups. Code that frees a brick and then counts the "bricks" group in the same frame gets a count that's one too high.Docs: Node.queue_free(). "Queues this node to be deleted at the end of the current frame."

3. Signals can carry data, and you connect to nodes you just made

Your ball_drained signal carried nothing. A signal can also pass values to its listeners:

signal destroyed(points: int)

func hit() -> void:
	self.destroyed.emit(self.points)
	self.queue_free()

Bricks made from code have no listener yet, so the game connects to each one right after creating it, before add_child():

brick.destroyed.connect(self._on_brick_destroyed)

func _on_brick_destroyed(points: int) -> void:
	self._score += points

That leaves one question: how does a brick know it was hit? A StaticBody2D has no "something bounced off me" signal. The ball is the one that finds out, because move_and_collide() hands it the collision, and collision.get_collider() is the brick. So the ball calls hit() on it. That isn't a parent calling a child. It's one node acting on a peer the physics engine introduced, and that's normal. Guard it, so the ball doesn't call hit() on a wall:

var collider: Node = collision.get_collider() as Node
if collider.is_in_group("bricks"):
	collider.hit()

One trade-off to notice: Godot can't check that a plain Node has a hit() method, so a typo there only fails when the line runs. if collider is Brick: would be checked, because class_name Brick makes it a type, like Ball and Drain. The group version accepts any node that plays the "brick" role. The class version accepts only that one script. Your spec picks one.

Put together: the ball calls across to the brick, the brick signals up with its points, and the game owns the score. The brick never knows the score exists, and the ball never knows about scoring.

Do it

Use /feature-spec for each spec, as you did for 0005–0008. Write your own answers before opening each model.

  1. Predict the node tree. On paper, write what the running game's tree will look like once there are 50 bricks and a score label. Which nodes are in game.tscn, and which only exist at runtime? Which nodes are in the "bricks" group? You'll compare in step 6.
  2. Spec 0009: rename main to game. Your idea from the recall. Do the rename yourself in the editor's FileSystem dock (right-click → Rename), so Godot updates every reference. Rename both main.tscn and main.gd, and the root node too. Then ask the agent to check that nothing still says "main", including run/main_scene in project.godot.
    Model spec (open after writing yours) 
    # 0009 · Rename main to game

Goal: the scene that owns game state is called Game.

Behaviour:
- main.tscn → game.tscn, main.gd → game.gd, root node Main → Game.
- Renamed in the editor's FileSystem dock so references update.
- run/main_scene points at game.tscn.

Done when:
- F5 runs the game exactly as before.
- Searching the project for "main" finds nothing but run/main_scene's key name.

Not in this spec:
- Any behaviour change, any other renames.

    A rename spec with no behaviour change sounds trivial. It's worth a commit of its own, so the bricks diff isn't buried under 30 renamed lines.

  3. Spec 0010: one brick. A single brick, placed by hand in game.tscn. The ball bounces off it and the brick disappears. Decide: its body type, size and colour, its collision layer, and what changes in the ball's mask. Then compare with the model.
    Model spec (open after writing yours) 
    # 0010 · One brick

Goal: a brick the ball breaks by hitting it.

Behaviour:
- Brick is a StaticBody2D with a ColorRect, 80x24, its own scene, in group "bricks".
- New collision layer 5 "bricks"; the ball's Mask adds "bricks".
- The ball bounces off it as off a wall, then calls hit() if the collider is in "bricks".
- hit() removes the brick with queue_free().
- One brick placed by hand in game.tscn, near the top centre.

Done when:
- The ball bounces off the brick and the brick disappears on the first hit.
- In Scene → Remote, the Brick node is gone after the hit.

Not in this spec:
- More bricks, score, multi-hit bricks, rebuilding bricks on reset.

    In review, check the bounce happens before hit(). The ball still needs the collision normal, and the order makes the intent obvious.

  4. Spec 0011: a grid from code. Replace the hand-placed brick with a grid the game builds in code. Decide the rows, columns and gap, which numbers are @export, and how the grid stays centred. Decide what reset_game() does about broken bricks: rebuild them, or leave them broken? Either is defensible; the spec must say.
    Model spec (open after writing yours) 
    # 0011 · Brick grid

Goal: a wall of bricks fills the top of the screen.

Behaviour:
- game.gd builds a grid from brick.tscn with preload + instantiate() + add_child().
- 5 rows × 12 columns, 4 px gap, centred horizontally, 60 px from the top.
- rows, columns, gap and top margin are @export vars on game.gd.
- The hand-placed brick from 0010 is removed.
- reset_game() leaves broken bricks broken (a miss isn't a new level).

Done when:
- Running the game shows 60 bricks; Scene → Remote lists them under Game.
- Changing columns in the Inspector before F5 changes the grid and it stays centred.

Not in this spec:
- Score, rebuilding bricks, level clear, brick colours by row.

    Watch where the agent creates bricks. In _ready() is right for this spec. Inside reset_game() would contradict "leaves broken bricks broken".

  5. Spec 0012: score. Each brick is worth points. The brick signals up with its points, the game adds them up, and a label shows the total. Decide: points per brick, where the label goes, and whether a miss resets the score.
    Model spec (open after writing yours) 
    # 0012 · Score

Goal: I see my score go up as I break bricks.

Behaviour:
- Brick has signal destroyed(points: int) and @export var points = 10; hit() emits it before queue_free().
- game.gd connects each brick's destroyed when it creates it, and adds points to _score.
- A Label in the top-left shows "Score: N", updated on every change.
- A miss does not reset the score.

Done when:
- Score starts at 0 and goes up by 10 per brick.
- The score is unchanged after a miss.

Not in this spec:
- High score, saving, lives, level clear, label styling.

    The review question: does the brick reference the label or the game? It shouldn't. It only emits.

  6. Run it and compare. Run the game and check every "Done when" line. Open Scene → Remote and compare the live tree with your prediction from step 1. Select a brick in Remote, open the Node dock, and find its group.
  7. Break it on purpose. In ball.tscn, untick bricks in the ball's Mask. Run it and describe what happens, and why. Then undo it with git checkout.
